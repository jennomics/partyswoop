# Real-time party request system with AI fridge scanning (v2)

PartySwoop is a Next.js 14 application implementing short-lived party management with real-time guest requests over SSE. The v1 review raised 7 issues — all have been addressed in this pass. The SSE event bus is documented as single-process, heartbeats are in place, the OpenAI call has a 30s timeout, rate limiting protects guest submissions, location code collisions retry, the CSRF security model is documented, and the useSSE hook closure leak is fixed with a stabilized ref.

Two new concerns remain after the fixes: the rate limiter trusts client-supplied `X-Forwarded-For` without validation, making it trivially bypassable by rotating the header value; and the scan endpoint still has no per-file size limit, allowing large uploads to exhaust server memory.

Watch for: Rate limit bypass via spoofed X-Forwarded-For header (confirmed). Unbounded image upload size on scan endpoint (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The rate limiter keys on the first value from `X-Forwarded-For`, falling back to `guestCode`. Without a trusted proxy configuration that strips or overwrites this header, any client can rotate it per-request and completely bypass the 10-request/60s limit. The fix is either to trust only a known proxy layer's header or to always use `guestCode` as the rate limit key (which bounds abuse per-party rather than per-IP).

The scan endpoint validates image count (max 5) but not individual file size. A single request with five 50MB images would buffer ~250MB into Node.js heap before the OpenAI call even begins. A `Content-Length` check or per-file stream size limit would prevent this without changing the API contract.

## Rate limit bypass via X-Forwarded-For spoofing

The guest request rate limiter extracts its key from the raw `X-Forwarded-For` header:

```typescript
const forwardedFor = request.headers.get('x-forwarded-for');
const rateLimitKey = forwardedFor?.split(',')[0]?.trim() || params.guestCode;
```

Any HTTP client can set `X-Forwarded-For: <random-value>` on every request, producing a unique rate limit key each time. The 10-request/60s window never fills because each "IP" is new. The fallback to `guestCode` only triggers when the header is entirely absent — a condition that never occurs behind most reverse proxies (which append rather than overwrite) or when an attacker deliberately provides the header.

The straightforward fix is to key on `guestCode` unconditionally. This limits abuse to 10 requests per 60 seconds per party link, which is the actual threat model (flooding a specific party). IP-based limiting is useful as a defense-in-depth layer but only works when the deployment guarantees the header is trustworthy (e.g., Cloudflare's `CF-Connecting-IP`, or a reverse proxy that overwrites `X-Forwarded-For`).

## Unbounded image memory allocation on scan

The scan endpoint reads all uploaded files into `Buffer` instances before passing them to the AI function:

```typescript
for (const file of files) {
  if (!(file instanceof File)) { ... }
  const arrayBuffer = await file.arrayBuffer();
  imageBuffers.push(Buffer.from(arrayBuffer));
}
```

There is no size check on individual files. The `File` object from `formData` provides a `.size` property that can be checked before calling `.arrayBuffer()`. Without this guard, a single request can force the server to allocate hundreds of megabytes. Combined with the fact that this endpoint is protected only by the hostCode (no rate limit applied to host endpoints), a compromised host link could be used to repeatedly OOM the server.

A practical limit of 5MB per file (25MB total for 5 images) would match the `detail: 'low'` setting already passed to OpenAI, which downscales images to 512x512 anyway — sending larger files provides no quality benefit.
