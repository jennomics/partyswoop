# Rate limit fix and scan upload size cap (v3)

This commit addresses the two remaining issues from the v2 review. The rate limiter now keys unconditionally on `guestCode`, eliminating the spoofable `X-Forwarded-For` vector. The scan endpoint rejects any file exceeding 5MB before calling `.arrayBuffer()`, preventing memory exhaustion from oversized uploads.

Watch for: No new blocking concerns identified. The two v2 issues are resolved.

**Verdict**: APPROVED

## High-level view

The rate limiter no longer reads `X-Forwarded-For` at all — it uses `params.guestCode` directly, which is server-resolved from the URL path. This bounds abuse to 10 requests per 60 seconds per party link, matching the actual threat model. There is no way for a client to influence the key.

The scan endpoint checks `file.size` against a 5MB constant before reading the file into memory. With 5 files max at 5MB each, worst-case memory per request is ~25MB. One caveat worth noting: Next.js buffers the full multipart body before `request.formData()` returns, so the size check prevents holding large buffers through the OpenAI call duration rather than rejecting them at upload time. True upload-time rejection would require middleware-level streaming, but that's outside scope for this application.
