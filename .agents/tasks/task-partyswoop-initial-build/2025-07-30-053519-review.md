# Real-time party request system with AI fridge scanning

PartySwoop is a greenfield Next.js 14 application that lets a host create a short-lived party, manage a drink/supply menu, and receive real-time guest requests via SSE. Guests scan a QR code or follow a link, pick a drink/supply/song/other, and track their request status live. The host dashboard shows an incoming request queue with forward-only status transitions (NEW -> SEEN -> DONE) and audio alerts. An optional OpenAI Vision integration detects drinks from fridge photos with a human-review step before publishing.

The architecture is straightforward: Next.js API routes backed by Prisma/PostgreSQL, an in-process event bus for SSE fan-out, and client components for both host and guest views. Party codes use a safe alphabet (no ambiguous characters) via nanoid. The 24-hour party expiry is checked server-side on every request.

Watch for: The in-process SSE event bus fails silently across multiple server instances or after a serverless cold start (confirmed). The OpenAI API call has no timeout, so a slow upstream stalls the request indefinitely (confirmed). Guest-facing request submission has no rate limiting, making request-flood abuse trivial (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The SSE implementation uses an in-memory singleton event bus that only works within a single Node.js process. In any scaled deployment (multiple containers, serverless functions, or even Next.js edge runtime), events published on one instance never reach subscribers on another. This is the most significant architectural constraint and it's undocumented.

Party access is entirely controlled by unguessable codes — hostCode for management, guestCode for guest access. There is no session, no authentication, no CSRF protection. The codes have good entropy (~46 bits), but a leaked hostCode link is a full compromise of that party's host controls with no rotation mechanism.

The AI fridge scan degrades gracefully — missing API key returns a 200 with `fallback: true` rather than an error. However, the `fetch()` call to OpenAI has no AbortController timeout, and there's no per-image file-size validation beyond the 5-image count limit, so large uploads buffer entirely into server memory.

The host's `RequestQueue` fetches requests once on mount then relies entirely on SSE for updates, with no polling fallback. The guest's `RequestTracker` compensates with visibility-change polling, but the host has no equivalent — a dropped SSE connection means missed requests until manual refresh.

<summary>Issues (7)</summary>

1. **In-process SSE bus breaks multi-instance deployment** — The singleton `SSEEventBus` only delivers events within the same process. Add Redis pub/sub, Postgres LISTEN/NOTIFY, or document the single-process constraint prominently.
2. **No request rate limiting on guest submissions** — The `/api/party/[guestCode]/requests` endpoint has no throttle. Add per-IP or per-guestCode rate limiting to prevent request flooding.
3. **OpenAI API call has no timeout** — `scanFridgePhotos` calls `fetch()` without an AbortController timeout. A stalled upstream hangs the request thread. Add a 15-30s timeout.
4. **Host API routes lack CSRF protection** — All state-mutating host endpoints accept any request with the correct URL. The JSON Content-Type requirement provides implicit CSRF protection via preflight, but this should be documented as a deliberate security boundary.
5. **SSE streams have no heartbeat** — Without periodic keep-alive messages, proxies and load balancers (ALB default: 60s idle) will terminate seemingly-idle connections. Add a 30s heartbeat interval.
6. **Location code collision is unhandled** — `generateLocationCode(6)` doesn't check for uniqueness before INSERT. The DB unique constraint will throw an unhandled Prisma error rather than retrying with a new code.
7. **useSSE reconnect creates event listener leaks** — The `eventTypes` array dependency in `useCallback` is a new array on every render, causing `connect` to be recreated but the `useEffect` only depends on `url`, so stale closures can accumulate EventSource instances on re-renders.

## In-process event bus and SSE scaling

The `SSEEventBus` class in `src/lib/sse.ts` is an in-memory pub/sub system attached to `globalThis` to survive Next.js hot reloads. When a guest submits a request, the API route calls `sseEventBus.publish(party.id, 'new-request', newRequest)` and any currently-connected host SSE stream on that same process receives it. Next.js in production (especially with `output: 'standalone'`) may run multiple worker processes, and serverless platforms run each request in an isolated function. The event bus Map lives in one process; subscribers connected to other processes never see the event.

```
Guest POST /api/party/X/requests
  -> sseEventBus.publish(partyId, 'new-request', data)
     -> process A subscribers: notified
     -> process B subscribers: never reached
```

The SSE streams also have no heartbeat/keep-alive. The response headers include `Connection: keep-alive` but no periodic data is sent. Intermediate proxies (AWS ALB, Cloudflare, nginx defaults) will terminate idle connections after 60-120 seconds of silence. A host who hasn't received a request in 60 seconds loses their SSE connection silently until the client's `onerror` fires and reconnects 3 seconds later — creating a window where events are lost permanently (no replay buffer exists).

## Guest request flood and missing rate limiting

The guest request endpoint at `/api/party/[guestCode]/requests` validates the request payload thoroughly but applies no throttle on submission volume. The guestCode is public (printed on QR codes, embedded in URLs). An automated client can submit hundreds of requests per second, each generating an SSE event and a database INSERT. There's no per-IP, per-session, or per-guestCode limit. This makes denial-of-service against a specific party trivial.

## OpenAI Vision integration without timeouts

The `scanFridgePhotos` function calls the OpenAI API via `fetch()` with no AbortController or timeout mechanism:

```typescript
const response = await fetch('https://api.openai.com/v1/chat/completions', {
  method: 'POST',
  headers: { ... },
  body: JSON.stringify({ model: 'gpt-4o-mini', messages: [...], max_tokens: 500 }),
});
```

If the OpenAI API is slow, the server-side request handler blocks indefinitely. Next.js API routes in standalone mode have no default timeout, so this could tie up a connection slot for minutes.

There's also no file-size validation beyond the 5-image count limit. The scan endpoint converts files to `Buffer` via `file.arrayBuffer()` for all uploaded images before sending them to OpenAI. Five 20MB images would allocate ~100MB of server memory for a single request.

## Host code as sole authorization

Every host operation is gated solely on knowing the `hostCode` (8 chars from 55-char alphabet, ~46 bits of entropy). Brute-force is impractical, but:

- The hostCode appears in URLs and browser history with no rotation mechanism
- There's no session timeout beyond the 24-hour party expiry
- All mutating endpoints are plain POST/PATCH/DELETE with no CSRF token

The JSON `Content-Type` requirement on all mutating endpoints triggers CORS preflight for cross-origin requests, which provides implicit CSRF protection. Since there are no cookies or credentials, this vector is largely blocked. The security model — "anyone with the URL is the host" — should be documented explicitly so future changes that add cookies or sessions don't accidentally open CSRF vectors.

## Location code uniqueness collision

`generateLocationCode(6)` produces a 6-character code from the 55-char alphabet (~30 bits of entropy). The `Location.code` field has a `@unique` constraint in the Prisma schema. If a collision occurs, the `prisma.location.create()` call throws a unique constraint violation that gets caught as a generic "Failed to create location" 500 error rather than retrying with a new code. A simple retry loop (max 3 attempts) would make this robust.

## SSE client reconnection and event loss on host

The `useSSE` hook reconnects on error after a 3-second delay. However, there's no event replay mechanism. The host's `RequestQueue` fetches requests once on mount and then relies entirely on SSE for updates — no periodic polling, no visibility-change refetch. A host who loses their SSE connection for any reason (proxy timeout, network blip, process restart) will miss requests submitted during the gap. They'll never appear in the queue without a manual page refresh. The asymmetry with the guest side (which has visibility-change polling) suggests this was an oversight.

The `useSSE` hook has a subtle closure issue: the `eventTypes` parameter is an array literal at the call site (e.g., `['new-request', 'request-update']`), creating a new reference each render. The `connect` callback depends on this via `useCallback`, but the `useEffect` only lists `url` as a dependency. The initial connection works, but if `url` changes without a remount, the new EventSource could use a stale `eventTypes` closure. More concretely, on HMR or fast re-renders, multiple EventSource instances could accumulate since `connect()` creates a new one without guaranteeing the old is closed before the effect cleanup runs.

## Test coverage gaps

Not tested:

- API routes (request/response cycle with database)
- SSE event delivery or the event bus publish/subscribe behavior
- Host dashboard's real-time update flow
- Party expiration enforcement
- Scan endpoint's file handling (FormData parsing, size limits)
- `useSSE` hook reconnection logic (mocked away in component tests)

The 53 passing tests validate pure functions and component rendering. The most complex behavior (SSE streaming, multi-step request flows, expiration guards) has zero automated coverage.
