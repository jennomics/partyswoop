# Inventory tracking, host request views, and guest queues

Adds four features to the party host/guest experience: host-side inventory tracking with auto-decrement on fulfillment, a multi-dimensional request views tab for the host, and guest-visible FIFO queues for song and supply requests. The approach keeps the data model minimal (two new columns on `menu_items`), performs all grouping/filtering client-side, and relies on existing SSE infrastructure for real-time updates. A bundled fix replaces the `process.env.DB` hack with `getCloudflareContext()`.

Watch for: the inventory decrement has a read-then-write race (confirmed), item matching by name is fragile to renames (confirmed), and `myRequestIds` is session-only state that doesn't survive page reloads (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The inventory system adds `quantity` and `low_stock_threshold` columns, a dedicated `/inventory` GET endpoint, and a `InventoryManager` component. When the host marks a drink or supply request as DONE, the fulfillment route looks up the matching menu item by name and decrements its quantity. This lookup uses a non-atomic read-then-write pattern without a transaction, which under concurrent fulfillment could double-decrement or skip the zero-availability cutoff.

Host request views introduce a single `RequestViews` component that fetches all requests up-front and performs client-side grouping by guest/location/item with status and category filters. The "By Guest" grouping maps `deliveryValue` to guest identity, which means location-based requests from anonymous guests show up under an "Unknown Guest" bucket with no way to trace them back.

The guest song and supply queue components are structurally identical: fetch all party-wide requests of that category, subscribe to SSE, and render three sections (active/queued/done). The guest's own requests are highlighted via `myRequestIds`, which is populated in component state on submission and lost on page reload or navigation away and back.

The `getDb()` refactor from `process.env.DB` to `getCloudflareContext()` is orthogonal to the four features but necessary to fix the runtime. It removes the `d1?` parameter, so any existing callers that passed a D1 binding explicitly (e.g., in tests) would break — though the existing test suite doesn't exercise DB calls directly.

<details>
<summary>Issues (6)</summary>

1. **Inventory decrement race condition** — The read-then-write in the fulfillment route (`findFirst` then `update`) is not wrapped in a transaction or D1 batch. Under concurrent fulfillment of the same item, quantity can go negative or miss the zero cutoff. Use `db.batch()` or a single UPDATE with a WHERE quantity > 0 guard.
2. **Name-based item matching is fragile** — Inventory decrement matches `menuItems.name === request.item`. If a host renames a menu item after a request is submitted, the decrement silently fails. Consider storing `menuItemId` on the request at submission time.
3. **myRequestIds lost on page reload** — The guest page tracks submitted request IDs in React state only. Navigating away or refreshing loses the highlight. Persist to `sessionStorage` or `localStorage` keyed by guestCode.
4. **RequestViews guest grouping for LOCATION deliveries** — Requests delivered to a location (deliveryType LOCATION) have no guest identifier, so grouping by guest puts them into "Unknown Guest." Either exclude them from the guest view or surface the limitation in the UI.
5. **No tests for new features** — All 53 tests are pre-existing. None of the four new API routes, the inventory decrement logic, or the new components have test coverage.
6. **SSE new-request event shape assumed but not validated** — The queue components cast `sseEvent.data` fields directly (`data.id as string`, `data.location as ...`). If the published event shape drifts (e.g., the supply queue expects `location` but the existing `new-request` publisher doesn't include it), the UI silently renders incomplete data.

## Inventory decrement without atomicity

The fulfillment route at `src/app/api/parties/[hostCode]/requests/[requestId]/route.ts` performs:

```ts
const matchingItem = await db.query.menuItems.findFirst({ ... });
if (matchingItem && matchingItem.quantity !== null && matchingItem.quantity > 0) {
  const newQuantity = matchingItem.quantity - 1;
  await db.update(menuItems).set({ quantity: newQuantity }).where(...);
}
```

Between the read and write, another request for the same item can be fulfilled concurrently. D1 supports batched transactions (`db.batch()`), and the codebase already uses this pattern in `src/app/api/parties/route.ts` for atomic party creation. A safer approach: use a single `UPDATE menu_items SET quantity = quantity - 1 WHERE id = ? AND quantity > 0` with a `RETURNING` clause, which avoids the TOCTOU window entirely.

If quantity goes to zero, the route sets `available = false`. But if two concurrent requests both read `quantity = 1`, both compute `newQuantity = 0`, and both write — the second write is a no-op on quantity but the `available = false` still fires, which is fine. The real risk is at `quantity = 2`: both read 2, both write 1, actual stock should be 0 but shows 1.

## Name-based item matching

```ts
eq(menuItems.name, existingRequest.item)
```

The `request.item` field is the menu item's name at the time the guest submitted the request. If the host renames "Modelo" to "Modelo Especial" between submission and fulfillment, the `findFirst` returns null and inventory isn't decremented. The menu item keeps its stale quantity. This is a data integrity gap worth addressing — either store the `menuItemId` on the request record (schema change), or match by ID rather than name.

## Guest queue highlight state is ephemeral

In `src/app/party/[guestCode]/page.tsx`:

```ts
const [myRequestIds, setMyRequestIds] = useState<string[]>([]);
```

This is populated only when `handleRequestSubmitted` fires. If the guest refreshes the page or navigates away, the IDs are gone. The queue still renders correctly (all party requests are shown), but the "You" badge disappears because the component has no way to identify which requests belong to the current guest. Persisting to `sessionStorage` or querying the guest's own requests from the API would fix this.

## RequestViews "By Guest" conflation

The grouping function:

```ts
case 'guest':
  key = req.deliveryType === 'NAME' ? req.deliveryValue : 'Unknown Guest';
```

Requests with `deliveryType === 'LOCATION'` have no guest name attached (the `deliveryValue` is the location ID/name). These all collapse into a single "Unknown Guest" bucket. For a host with mixed location-based and name-based deliveries, this bucket becomes a dumping ground. The grouping is technically correct but behaviorally confusing for the host.

## No test coverage for new features

The test suite has 53 tests, all pre-existing. None of the following are tested:

- `/api/parties/[hostCode]/inventory` GET endpoint
- `/api/party/[guestCode]/requests/songs` GET endpoint
- `/api/party/[guestCode]/requests/supplies` GET endpoint
- Inventory decrement logic in the fulfillment route
- `InventoryManager`, `RequestViews`, `SongQueue`, `SupplyQueue` components

Given the portfolio quality bar, the inventory decrement logic (the most complex behavior) and the API routes deserve unit tests at minimum.

## SSE event shape drift in queue components

The `SongQueue` component handles `new-request` events by destructuring fields:

```ts
const newSong: SongQueueItem = {
  id: data.id as string,
  item: data.item as string,
  deliveryValue: data.deliveryValue as string,
  ...
};
```

The `SupplyQueue` does the same but also expects `data.location`. The `new-request` SSE event is published from `src/app/api/party/[guestCode]/requests/route.ts` (the guest submission endpoint). If that publisher returns the request without the `location` join, the supply queue renders a null location. This depends on what the existing publisher emits — if it publishes the raw insert result (no join), the location field will be absent from the event.

## Bundled getDb() refactor

The `src/lib/db.ts` change from `process.env.DB` to `getCloudflareContext()` and the removal of the optional `d1?` parameter is a fix for the Cloudflare Workers runtime. This is unrelated to the four features and should ideally be a separate commit (it already is: `53be83a`). The `CloudflareEnv` interface declaration in `env.d.ts` properly types the `DB` binding. The change means `getDb()` can only be called within a request context where Cloudflare's async local storage is available — calling it outside (e.g., in a top-level module scope or in tests) would throw.
